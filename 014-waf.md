## WAF - IP Allowlisting with Coraza

## Pre-requisites
This lab assumes that you have completed the setup in `001` and `002`

## Lab Objectives
- Understand how Enterprise Kgateway uses Coraza as its WAF engine
- Configure a WAFPolicy with IP allowlisting using `@ipMatch`
- Apply the WAF policy to an HTTPRoute using EnterpriseKgatewayTrafficPolicy
- Test IP-based access control
- Understand source IP preservation considerations for load-balanced environments

## Understanding WAF in Enterprise Kgateway

Enterprise Kgateway uses **Coraza** (not ModSecurity) as its Web Application Firewall engine. Coraza is an open-source, OWASP ModSecurity-compatible WAF that supports the SecRule language, enabling you to write rules for request filtering, IP allowlisting, and more.

WAF policies in Enterprise Kgateway are configured through two resources:
1. **WAFPolicy** (`waf.solo.io/v1alpha1`): Defines the WAF rules using Coraza's SecRule syntax
2. **EnterpriseKgatewayTrafficPolicy** (`enterprisekgateway.solo.io/v1alpha1`): Attaches the WAF policy to specific routes or gateways using the `entWAF` field

## IP Allowlisting Use Case

A common security requirement is restricting access to your services to a known set of IP addresses or CIDR ranges. This is useful for:
- Limiting API access to trusted partners or internal networks
- Restricting admin endpoints to corporate IP ranges
- Implementing geo-based access restrictions
- Compliance requirements that mandate IP-level access control

## Create a WAFPolicy for IP Allowlisting

Create a `WAFPolicy` that uses Coraza's `@ipMatch` operator to allow only requests from specific IP ranges:

```bash
kubectl apply -f - <<EOF
---
apiVersion: waf.solo.io/v1alpha1
kind: WAFPolicy
metadata:
  name: ip-allowlist
  namespace: httpbin
spec:
  ruleEngineSettings:
    inline: |
      SecRuleEngine On
  customDirectives:
    - inline: |
        SecRule REMOTE_ADDR "!@ipMatch 203.0.113.0/24,198.51.100.50" \
          "phase:1,deny,status:403,id:1,msg:'IP not in allowlist'"
EOF
```

This configuration:
- Enables the Coraza rule engine with `SecRuleEngine On`
- Creates a rule that inspects `REMOTE_ADDR` (the client's IP address)
- Uses `!@ipMatch` to negate the match — if the IP is **not** in the allowlist, the rule triggers
- Allows the CIDR range `203.0.113.0/24` (256 addresses) and the single IP `198.51.100.50`
- Denies non-matching requests in `phase:1` (request headers phase) with a `403 Forbidden` status

Verify the WAFPolicy was created:
```bash
kubectl get wafpolicy -n httpbin
```

Expected output:
```
NAME             AGE
ip-allowlist     5s
```

## Apply the WAF Policy to the HTTPRoute

Create an `EnterpriseKgatewayTrafficPolicy` to attach the WAF policy to the httpbin route:

```bash
kubectl apply -f - <<EOF
---
apiVersion: enterprisekgateway.solo.io/v1alpha1
kind: EnterpriseKgatewayTrafficPolicy
metadata:
  name: waf-ip-policy
  namespace: httpbin
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: httpbin-route
  entWAF:
    wafPolicyRef:
      name: ip-allowlist
EOF
```

This policy:
- Uses `entWAF` with a `wafPolicyRef` to reference the WAFPolicy
- Targets the `httpbin-route` HTTPRoute

Verify the policy was created and attached:
```bash
kubectl get enterprisekgatewaytrafficpolicies -n httpbin
```

Expected output:
```
NAME             ACCEPTED   ATTACHED
waf-ip-policy    True       True
```

## Test the IP Allowlisting

Set up the gateway IP for testing:
```bash
export GATEWAY_IP=$(kubectl get svc -n enterprise-kgateway --selector=gateway.networking.k8s.io/gateway-name=ingress -o jsonpath='{.items[*].status.loadBalancer.ingress[0].ip}{.items[*].status.loadBalancer.ingress[0].hostname}')
```

Send a request — since your client IP is likely not in the `203.0.113.0/24` or `198.51.100.50` allowlist, the request should be denied:
```bash
curl -i "$GATEWAY_IP/get" \
  -H "content-type: application/json" \
  -H "Host: httpbin.glootest.com"
```

Expected output (request blocked):
```
HTTP/1.1 403 Forbidden
content-length: 0
server: envoy
```

The `403 Forbidden` response confirms that the WAF is active and your IP is not in the allowlist.

## Update the Allowlist with Your IP

To allow your own traffic through, first find your client IP:
```bash
# If testing from a machine with internet access:
MY_IP=$(curl -s ifconfig.me)
echo "My IP: $MY_IP"
```

**Note:** Make sure you ran the `MY_IP` export command above before applying this policy. If `MY_IP` is not set, the rule will have a malformed IP list.

Update the WAFPolicy to include your IP:
```bash
kubectl apply -f - <<EOF
---
apiVersion: waf.solo.io/v1alpha1
kind: WAFPolicy
metadata:
  name: ip-allowlist
  namespace: httpbin
spec:
  ruleEngineSettings:
    inline: |
      SecRuleEngine On
  customDirectives:
    - inline: |
        SecRule REMOTE_ADDR "!@ipMatch ${MY_IP},203.0.113.0/24,198.51.100.50" \
          "phase:1,deny,status:403,id:1,msg:'IP not in allowlist'"
EOF
```

Test again — the request should now succeed:
```bash
curl -i "$GATEWAY_IP/get" \
  -H "content-type: application/json" \
  -H "Host: httpbin.glootest.com"
```

Expected output:
```
HTTP/1.1 200 OK
content-type: application/json
server: envoy
x-envoy-upstream-service-time: 5
...
```

## Important: Source IP Preservation

When a load balancer sits in front of the gateway (common in cloud environments), `REMOTE_ADDR` will be the **load balancer's IP**, not the original client's IP. This means your allowlist rules may not work as expected.

To ensure the client's real IP reaches the WAF, you may need to configure source IP preservation:

1. **Set `externalTrafficPolicy: Local`** on the gateway Service to preserve the source IP:
   ```bash
   kubectl patch svc -n enterprise-kgateway \
     $(kubectl get svc -n enterprise-kgateway --selector=gateway.networking.k8s.io/gateway-name=ingress -o jsonpath='{.items[0].metadata.name}') \
     -p '{"spec":{"externalTrafficPolicy":"Local"}}'
   ```

2. **Configure `useRemoteAddress`** and **`xffNumTrustedHops`** on the gateway to trust the `X-Forwarded-For` header from the load balancer. These settings tell Envoy how many proxy hops to trust when determining the real client IP.

Without these configurations, the WAF rule will see the load balancer's IP as `REMOTE_ADDR` and may incorrectly allow or deny traffic.

## Advanced: Combining IP Allowlisting with OWASP Rules

**Note:** Make sure you ran the `MY_IP` export command from the earlier section before applying this policy.

You can combine IP allowlisting with additional Coraza rules for defense in depth. These rules use `QUERY_STRING` with `@rx` regex matching in phase 1, since query parameters in `QUERY_STRING` remain URL-encoded:

```bash
kubectl apply -f - <<EOF
---
apiVersion: waf.solo.io/v1alpha1
kind: WAFPolicy
metadata:
  name: ip-allowlist-with-owasp
  namespace: httpbin
spec:
  ruleEngineSettings:
    inline: |
      SecRuleEngine On
  customDirectives:
    - inline: |
        SecRule REMOTE_ADDR "!@ipMatch ${MY_IP},203.0.113.0/24,198.51.100.50" \
          "phase:1,deny,status:403,id:1,msg:'IP not in allowlist'"
    - inline: |
        SecRule QUERY_STRING "@rx (?i:union.*select|select.*from|drop\s+table|insert\s+into)" \
          "phase:1,deny,status:403,id:2,msg:'SQL injection detected'"
    - inline: |
        SecRule QUERY_STRING "@rx (?i:%3Cscript|<script|javascript:|onerror=|onload=)" \
          "phase:1,deny,status:403,id:3,msg:'XSS detected'"
EOF
```

This layered approach:
- First checks if the client IP is in the allowlist
- Then inspects the query string for SQL injection patterns (UNION SELECT, SELECT FROM, etc.)
- Then inspects the query string for XSS patterns (matching both raw and URL-encoded `<script>` tags)

**Note:** `QUERY_STRING` contains the raw URL-encoded query string, so the XSS regex matches both `<script` and `%3Cscript` to catch encoded payloads.

Update the traffic policy to use this combined WAF policy:
```bash
kubectl apply -f - <<EOF
---
apiVersion: enterprisekgateway.solo.io/v1alpha1
kind: EnterpriseKgatewayTrafficPolicy
metadata:
  name: waf-ip-policy
  namespace: httpbin
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: httpbin-route
  entWAF:
    wafPolicyRef:
      name: ip-allowlist-with-owasp
EOF
```

Test SQL injection detection (should be blocked even from an allowed IP):
```bash
curl -i "$GATEWAY_IP/get?id=1%20UNION%20SELECT%20*%20FROM%20users" \
  -H "content-type: application/json" \
  -H "Host: httpbin.glootest.com"
```

Expected output:
```
HTTP/1.1 403 Forbidden
content-length: 0
server: envoy
```

Test XSS detection:
```bash
curl -i "$GATEWAY_IP/get?name=%3Cscript%3Ealert(1)%3C/script%3E" \
  -H "content-type: application/json" \
  -H "Host: httpbin.glootest.com"
```

Expected output:
```
HTTP/1.1 403 Forbidden
content-length: 0
server: envoy
```

## Cleanup

Remove the WAF traffic policy:
```bash
kubectl delete enterprisekgatewaytrafficpolicy -n httpbin waf-ip-policy
```

Remove the WAFPolicies:
```bash
kubectl delete wafpolicy -n httpbin ip-allowlist
kubectl delete wafpolicy -n httpbin ip-allowlist-with-owasp 2>/dev/null || true
```

If you changed the external traffic policy, revert it:
```bash
kubectl patch svc -n enterprise-kgateway \
  $(kubectl get svc -n enterprise-kgateway --selector=gateway.networking.k8s.io/gateway-name=ingress -o jsonpath='{.items[0].metadata.name}') \
  -p '{"spec":{"externalTrafficPolicy":"Cluster"}}'
```

Verify cleanup:
```bash
kubectl get enterprisekgatewaytrafficpolicies -n httpbin
kubectl get wafpolicy -n httpbin
```

Test that requests are no longer filtered:
```bash
curl -i "$GATEWAY_IP/get" \
  -H "content-type: application/json" \
  -H "Host: httpbin.glootest.com"
```

The request should return `HTTP/1.1 200 OK`.

## Key Takeaways

- Enterprise Kgateway uses **Coraza** (not ModSecurity) as its WAF engine
- WAF policies are configured using `WAFPolicy` (defines rules) and `EnterpriseKgatewayTrafficPolicy` with `entWAF` (applies the policy)
- The `@ipMatch` operator in Coraza SecRules enables IP-based allowlisting and denylisting
- Source IP preservation (`externalTrafficPolicy: Local`, `useRemoteAddress`, `xffNumTrustedHops`) is critical when a load balancer sits in front of the gateway
- WAF rules can be layered — combine IP allowlisting with OWASP protections like SQLi and XSS detection
